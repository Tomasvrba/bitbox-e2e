bitbox-e2e

Every PR gets an automatic e2e run
with device screenshots as evidence

One command builds the PR's firmware simulator, picks the scenarios that reach the changed code, shows the maintainer exactly which device screens changed, and flags anything that broke in pre-existing vectors and in the api-go / api-rs / api-ts suites. Native, no docker, about 1.5 minutes per PR.

Why

Today, checking a device change is manual

Hand testing on the simulator

Someone builds the simulator, clicks through the flow and eyeballs the screens. Nobody sees what the reviewer saw; there is nothing to attach to the PR.

Unit tests check strings, not flows

Firmware tests assert Screen:: values against a mock UI. They don't render pixels, and they don't run the host API end to end.

Cross-repo drift goes unnoticed

Firmware changed the high-fee wording for 9.28.0 and updated its vectors. The copies in api-go, api-rs and api-ts were not updated. Their CI only tests released simulators, so it is green today and will break when 9.28.0 ships.

found by this harness

Prior art

Trezor (--ui=test, fixture hashes, HTML diff report) and Ledger (Speculos + Ragger golden PNGs) both do this. BitBox had the pieces (simulators, vectors) but not the pipeline.

How it works

One PR run, two lanes

PRfirmware, API or app change
→
Selectcoverage map: changed functions → units that execute them
→
Lane A · evidencerun selected units on the head simulator, diff screens against the merge-base baseline bundle (text + LCD pixels)
Lane B · regressioncheck every unit with expectations; run api-go / api-rs / api-ts against the head simulator, with their own and the firmware's vectors
→
Reportreport.html + PR comment: changed screens, failures, unreached code

Units

A unit is one scripted host session: a scenario in scenarios/*.json or a firmware BTC vector. Each runs headless (exact screen text) and, when its screens changed, on the graphical simulator (real LCD pixels, driven by touch gestures).

Baseline bundle

Built once per master commit: every unit's screens, frames, API results and the coverage map. PR runs reuse it, so only the head is built and run.

Expectations are optional

Without them, lane A still shows what changed. A maintainer can promote approved screens; from then on they are a regression check.

Reading it

The API repos carry copies of btc-transaction-test-vectors.json with the old wording. Against a 9.28.0 simulator their own suites fail; with the firmware's current vectors they pass. Fix: refresh the copies before 9.28.0 is added to their CI.

Expectations

All 28 selected vectors pass the 9.28.0 expectations on head. On the base commit the same 28 fail, which is exactly the change under review.

BitBoxApp

App changes: Playwright against the same simulator

watch-only.test.ts, head, Chromium, simulator device connected

e2e.py wallet-compare runs the app's own Playwright tests from clean clones of base and head, with a natively built simulator. The report lists per-test status, errors, device screen diffs and final screenshots that differ.

Contributor workflow

No expectations to write up front

1 · Open the PR

CI runs e2e.py pr against the merge-base bundle and posts the report.

2 · Unreached code?

The report lists changed functions no unit reaches. The bitbox-e2e Claude skill drafts a scenario (or a driver op) for them, runs it locally and attaches the evidence.

3 · Maintainer reviews screens

Approve what the device shows, or ask for changes, from the report.

4 · Promote

e2e.py promote <out> scenario/x writes the approved screens as a version-ranged expectation.

<!-- e2e   optional PR-body block (planned)
units: btc-vector/*fee*, scenario/eth-erc20-*
graphical: btc-vector/*fee*
api-rs: my-branch   # unreleased API call
-->

Adds to the automatic selection, never replaces it. Useful for showcase screenshots of a new flow, or when the driver needs an unreleased bitbox-api-rs branch.

CI

  • Standard GitHub runners, free on public repos; expect ~2× on 4 vCPU
  • No GPU, no hardware: Xvfb + software GL
  • Baseline + coverage map per master merge: ~10–15 min (two simulator builds dominate)
  • Storage: a few MB per bundle; app videos only on failure

Not covered

  • Hardware-only code (~15% of firmware commits): bootloader, BLE, secure chip
  • BitBox03 UI until its graphical simulator is wired in

Use it

Commands

# once per machine (no root): LLVM, protoc, Rust pin, node, driver
e2e/setup.sh

# a PR, against its merge-base; WORKTREE = uncommitted firmware checkout
e2e/e2e.py pr --base bitbox/master --head my-branch --out /tmp/e2e/my-pr

# baseline bundle + coverage map for a master commit (CI does this per merge)
e2e/e2e.py baseline bitbox/master
e2e/coverage.py map bitbox/master

# what a diff reaches, and what it doesn't
e2e/coverage.py select --base bitbox/master --head my-branch --summary

# accept reviewed screens as expectations
e2e/e2e.py promote /tmp/e2e/my-pr scenario/eth-erc20-unknown

# app change
e2e/e2e.py wallet-compare --base bitbox/master --head my-branch --firmware bitbox/master \
  --out /tmp/e2e/app tests/watch-only.test.ts
