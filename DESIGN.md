# Design: automatic e2e evidence and regression per PR

Goal: every firmware, API, app or Rabby change gets an automatic e2e run that (A) shows the maintainer what
the change looks like on the device, as screens that differ from the merge-base, and (B) flags
anything pre-existing that broke. Expected results are optional; they accumulate when a
maintainer promotes approved screens.

## Lanes

- **A, evidence** (`e2e.py pr`): run every unit headless on the head simulator and diff each
  against the merge-base baseline bundle. Report only differing/new screens, plus the changed
  firmware functions that no unit reached and the changed files coverage cannot see.
- **B, regression** (`e2e.py pr`, same run): every unit that has expectations is checked on head
  (pass/fail), and the api-go/api-rs/api-ts simulator suites run against the head simulator,
  once with their committed vector copies (drift) and once with the firmware's vectors.

The report is the product; the gate is secondary and fires only on regressions against the
merge-base. `pr` exits 1 when a unit that completed on base fails on head, when a BTC vector that
must be rejected (its `outcome` for the head version) was rejected on base and completes on head,
or when an API test
that passed on base fails on head or an API suite errors on head (build, crash, no tests ran); 2
when the harness itself fails; else 0. For a firmware change only the API run with the firmware's
vectors gates; failures with the API repos' committed vector copies are drift, reported only. For
an API change both runs gate. Expectation mismatches and changed screens are reported, never
gating. `e2e.verdict` computes the reasons from `pr.json` data.

## The repo under test

`e2e.py pr --repo <repo>` takes base and head in one of `bundle.REPOS` (firmware, app, api-rs,
api-go, api-ts, rabby) and compares head with `merge-base(base, head)` in that repo. Every other
repo is the same on both sides: its `--pin <repo>=<ref>`, else the default (upstream `master` for
the firmware and the app, Rabby v0.94.15; for the API repos the sibling checkout's `HEAD` in the
device flow, which in CI is the upstream default branch, and the shipped version in the app and
Rabby flows).

A change runs several flows (`e2e.FLOWS`): its own tests, then the integrations built on the changed
repo. The integrations are the point for the BitBox repos: a firmware, api-go or api-ts change can
break the app or a third-party wallet without failing any test of its own (bitbox-wallet-app#4579).

- firmware, api-*: lanes A and B. A side is (firmware commit, API revisions); the base side is a
  bundle, keyed by the firmware sha and, if any API revision is pinned, a hash of those revisions.
  The driver links the side's `api-rs` (`runs.driver_for`: the pinned commit, built in a cache
  layout that satisfies its `../../bitbox-api-rs` path dependency; else the sibling tree).
- app (`wallet_app.compare`), wc (`wc.flow.compare`), rabby (`rabby_e2e.compare`): each takes
  `sides` ({"changed", "base": {repo: ref}, "head": {...}}, written to `sides.json`) and builds what
  differs: a simulator per firmware commit, the app against the side's api-go (go mod replace +
  vendor), Rabby with the side's api-ts (npm pack as its dependency). Run into `--out/<flow>` unless
  the flow is the repo's first; `report.with_flows` puts their findings on the run's page.

`ci/pr.sh` is the same entry point for CI: it validates the form's inputs, fetches head from a fork
and passes commits to `e2e.py pr`.

## Report

Each flow (`e2e.pr_findings`, `wallet_app.wallet_report`, `wc.flow.report`, `rabby_e2e.report`) turns its run
directory into one `findings` dict (format in `report.py`): what broke, what changed on the device,
what was there before, what was tested. `report.render` writes `report.html` (images linked
relative to the directory, every one listed in `report-files.txt` for a publish step) and
`summary.md` (for the CI run page and the PR comment). Text in findings comes from the code under
test and the PR description: the page escapes it, the summary escapes Markdown outside code spans.
With `--pr-info`, the report shows the PR, and the `expect:` globs of its `<!-- e2e -->` block mark
each change as expected or not. No step of a run uses a language model: the report is rendered
from the run's data only.

## Units

A unit is one scenario run. `units.load_units(firmware_dir, scenarios_dir)` returns a list of

```python
{
  "id": "scenario/eth-erc20-known" | "eth-matrix/<chain id>-<case>" | "btc-vector/<vector name>",
  "kind": "scenario" | "btc-vector",
  "scenario": {"name": ..., "description": ..., "steps": [...]},  # driver input, same as scenarios/*.json
  "expect": [ {"min_version": "9.28.0", "max_version_exclusive": null, "screens": [...]}, ... ] | None,
}
```

- `scenarios/*.json` units: `expect` comes from an optional `expect` key in the file.
- `eth-matrix/*` units are generated by `eth_matrix.py` (kind `scenario`); their `expect` comes from
  `scenarios/eth-matrix/<chain id>-<case>.json` (`{"expect": [...]}`), created by the first `promote`.
- BTC vector units come from `<firmware>/src/rust/bitbox-test-vectors/testdata/btc-transaction-test-vectors.json`; one unit per
  vector, `expect` from its version-ranged expectations. The driver op is `btc-sign-psbt`.
- `expect.check(unit, screens, simulator_version) -> {"status": "pass"|"fail"|"no-expectation", "diff": str}`
  picks the expectation whose version range contains the simulator version.
- `e2e.py promote <pr-out-dir> <unit-id>...` writes head screens into the scenario's `expect`
  for the head simulator version (scenario units only; vectors are owned by the firmware repo).
  `pr.json` stores the scenario path relative to the harness checkout; promote resolves it locally
  and refuses anything outside `scenarios/`.

Screens are the `screens.json` list `run_headless` writes (headless simulator transcript).

## Baseline bundle

`e2e.py baseline <firmware-ref> [--pin <api repo>=<ref>...] [--graphical <glob>...]` writes
`$BITBOX_E2E_CACHE/baselines/<sha>/` (with pins `<sha>-<pins hash>/`):

```
manifest.json                 {sha, simulator_version, harness_sha, created, pins, revisions, units: {id: {headless_ok, graphical_ok}}}
units/<id-slug>/headless/     screens.json, combined.log, driver.jsonl
units/<id-slug>/graphical/    frames.json, *.png      (only units selected for graphical)
apis/                         lane-B results for this ref
coverage/map.json             function -> unit ids (from the instrumented build)
```

`revisions` is what else was under test: `driver bitbox-api-rs` (the sibling tree the driver links,
`+dirty` if modified) and each API suite's repo revision. `pr.json` has the same for head
(`head.revisions`); the report flags differences without gating. A ref without the firmware's BTC
vectors file has no btc-vector units and no firmware-vector API run (`base.vectors`/`head.vectors`).

PR runs reuse it (keyed by the merge-base sha) and only run head. It lives in the cache; a manifest
without the current `format` (`bundle.BUNDLE_FORMAT`) is recorded again. Planned: CI publishes
bundles and prebuilt simulators as release files of this repo, so runs skip recording them.

## Coverage map and selection

- `build-sim.sh --coverage <ref>`: instrumented headless simulator at `sims/<sha>-cov/`.
- `coverage.py map <ref>` runs every unit headless on it, one profile per unit, and writes
  `coverage/map.json`: `{"functions": {"<file>::<function>": [unit ids]}, "lines": {"<file>": {"<line>": [unit ids]}}}`.
- `coverage.py select --base <sha> --head <ref>`: changed lines in Rust files linked into the
  simulator → units executing them, the changed functions/lines that no unit executes, and the
  changed files the map has no lines for (`unmapped`). Changed lines in head that do not exist in
  base are mapped by function name. `pr` reports the unreached functions and unmapped files; the
  selected units do not limit or extend what it runs.

## Parallel runs

Headless units, and graphical units whose `simulator-graphical` has `--port` (detected per
binary), start their simulator on a free port and run side by side; no network namespace needed.
Older graphical simulators bind 15423 only: each run goes into `isolated.sh` (private network
namespace) where namespaces exist, else they run one at a time. The API suites hardcode 15423:
concurrent in namespaces, else one at a time. Whether namespaces exist is probed once
(`isolated.sh true`); `pr.json` `run_mode` and the report record what ran how. Every Xvfb picks
its own display (`-displayfd`). In a namespace Xvfb takes `:0` without a lock file, so
`isolated.sh` also gives each namespace a private `/tmp/.X11-unix`: python-xlib connects to the
socket file there before the per-netns abstract socket. Build outside a namespace (no network inside); `E2E_DRIVER=<path>`
uses a prebuilt driver and skips the cargo build.

A bundle that is reused does not need the merge-base simulator; it is built only to record a
bundle or to add missing base-side graphical runs.

## WalletConnect flow (`e2e.py wc`, `wc/`)

App-driven, unlike units: the BitBoxApp backend is the device host. Per app ref, Playwright runs
`wallet/tests/walletconnect.test.ts` in the app clone; it spawns `wc/device.py` (graphical simulator,
JSON lines on stdio: `step <name>` labels frames, auto-accepts with `gsim.Recorder` like every graphical run) and
`wc/dapp.mjs` (sign-client, JSON lines: `next` sends the next request, results carry the
dapp-side signer check). Evidence per side: `app/steps.json` + PNGs, `device/frames.json` + PNGs.
The report aligns them by step name.

It needs the public WalletConnect relay and the app's Etherscan proxy, so it runs in the host
netns: not on fork PRs without network/secrets, not offline, one run per host at a time. The
project ID is the app's own (`WCWeb3WalletProvider.tsx`, override with `WC_PROJECT_ID`). Units of
kind `"wc"` (one dapp request each) can plug into `units.load_units` later; today the request
list is `REQUESTS` in `dapp.mjs`.

## Rabby flow (`e2e.py rabby`, `rabby/`, `bridge/`)

Wallet-driven like `wc`, but offline and reproducible: Rabby's backend is a recorded fixture
(`rabby/api_proxy.py`), chains are local anvils, the device link is `bridge/sim_bridge.py`. One
run (`rabby/run.py`, inside `isolated.sh`) is one fixed request list in `rabby/flow.ts`; flow.ts and
run.py use the driver's protocol (JSON lines, `step-start` waits for `go`), so device frames are
labelled by step. Evidence per side: `frames.json` + `device/*.png`, `shots.json` + `rabby/*.png`.

Units of kind `"rabby"` are a later integration: a unit would be one dapp request
(`{"method", "params", "chain"}`) instead of a driver step, run by a flow.ts that takes the request
list as input, with onboarding as its setup step. `units.load_units` would read them from
`rabby/*.json`; `pr`/`baseline` would run them through `rabby/run.py` instead of the driver, and
their frames slot into the existing graphical diff (`frames.json` has the same shape). Each new
request needs its API responses in the fixture (`rabby_e2e.py record`).
